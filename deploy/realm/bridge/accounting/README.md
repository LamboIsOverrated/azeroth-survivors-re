# Closed LIVE accounting kernel

Private implementation and fixture tests only. Nothing imports this module in the gateway or world server. The withdrawal extension can call explicitly injected sign-only/RPC adapters; no production adapters, keys, public routes or activation flags are configured here. Tests use published fixture signatures and simulated sends, with no actual network transaction. Existing TEST balances and the earlier withdrawal prototype are separate and are **never** copied here. The current TEST bridge is not a valid LIVE adapter.

## Interface

`createAccounting({path,config,rpc,archiveRpc,signer,resolveWallet,world,clock=Date.now})` returns a frozen facade. Use a new dedicated SQLite path. `config` requires `phase:'LIVE'`, `namespaceId`, `genesisHash`, conventional SPL `mint`, `decimals`, `treasuryWallet`, `treasuryTokenAccount` and a positive canonical decimal `atomsPerGameUnit`. This complete namespace and its conversion become immutable on creation. A foreign/TEST/prototype database, incomplete schema or changed configuration fails closed.

Amounts and character GUIDs are canonical decimal strings; account IDs are bounded positive integers. Never pass floating point money. Game units are capped at 2147483646; atoms and aggregate claims use raw u64. Every batch balances exactly, claims stay nonnegative, world claims are exact conversion multiples, and total claims equal recorded reserve assets.

Methods:

- `createDeposit({accountId,id,atoms,sourceTokenAccount})` creates a 15 minute account/wallet/config-bound intent. `resolveWallet(accountId)` must read a previously signature-bound account wallet. `rpc.call(method,params)` is a trusted read-only Solana adapter.
- `confirmDeposit({accountId,id,signature})` verifies finalized status, genesis, the actual Ed25519 signed legacy TransferChecked/memo receipt, exact source/mint/program/treasury/deltas, conventional mint/account bytes, and observed finalized treasury coverage before one immutable credit. It reuses the pure verifier, **not** the old settlement journal.
- `fundPool({id,accountId,poolId,atoms})` transfers existing vault claims into a system pool; it never creates backing.
- `reserveWithdrawal({accountId,id,atoms,destinationTokenAccount})` transfers existing available vault claims to `withdrawal_reserved`, binding the account's server-resolved signing wallet and validated destination. It requires configured sign-only/primary/archive adapters and shares the world/event account lock; amounts already in world/pool/escrow holds cannot be withdrawn.
- `prepareWithdrawal(accountId,id)` verifies the finalized blockhash's exact origin with `getBlock`, and persists its immutable unsigned plan and actual origin slot/height before signing. It validates the complete conventional SPL TransferChecked/memo transaction returned by `signer.signTransaction(unsignedBytes)`, then durably stores its exact signed bytes/signature before any send. It never infers an origin from an assumed blockhash-validity constant. The signer must not broadcast. `broadcastWithdrawal(accountId,id)` records pending before the injected RPC send and can only resend that same saved transaction; it needs no signer once bytes are durable.
- `reconcileWithdrawal(accountId,id)` requires a finalized matching raw signed transaction, not status alone. Success reduces recorded external reserve and reserved claims together; proven failure restores the vault once. Expiry requires a separate reviewed `archiveRpc.proveCompleteAbsence(request)` capability and `completenessPolicyId`, binding provider/genesis/config/signature, the saved blockhash origin, the entire valid block-height window and a finalized post-expiry boundary. The two sources' finalized heights, invalidity, retained-block floors and null lookups are only corroboration: they do not establish complete indexing. Missing, incomplete, pruned or conflicting evidence keeps the hold. No production completeness provider is implemented here. Terminal proofs retain the checked raw transaction/deltas or full bound completeness witness for offline audit; see `WITHDRAWALS.md` for its exact contract and official RPC references.
- `withdrawal(accountId,id)` is owner-scoped; `pendingWithdrawals({afterId:null,limit:50})` provides a private capped cursor-based recovery sweep. Complete sweeps must repeat to discover newly inserted earlier IDs. RPC/signing configuration is unnecessary for these reads.
- `prepareWorld({id,accountId,guid,kind,units,poolId?,eventId?,reason?})` reserves claims and commits an outbox entry before world mutation. Kinds: `grant` vault→world, `redeem` world→vault, `issue` funded pool→world, `sink` world→pool. `issue` requires a globally unique authoritative `eventId` and one of `quest`, `loot`, `vendor-sale`, `starting-money`. This is a trusted server API, never a client reward endpoint.
- `advanceWorld(accountId,id)` reconciles or applies once via the world adapter, validates a bound receipt, moves claims atomically, then acknowledges the durable accounting batch. Timeouts never refund. It retries only acknowledgement after local settlement. It releases the local character lock only after a matching world acknowledgement.
- `operation(accountId,id)`, `character(accountId,guid)`, `balance(accountId)`, `pool(poolId)`, `totals()`, `close()` inspect state. `balance` reports available vault and allocated world claims; reserved claims remain conserved but are unavailable. `AccountingStore` is an internal primitive and must not be exposed to request handlers.

## Mandatory world adapter contract

`authorizeCharacter(request)` returns `{phase:'LIVE',namespaceId,configHash,accountId,guid,moneyUnits,version}`. New characters must have zero money. Existing snapshots must exactly match backed local allocation and version. An authoritative ownership change, nonzero stock balance or unexplained save/version divergence fails closed.

`readReceipt(operation)` returns a durable bound receipt or null. Null permits idempotent `apply(operation)` under the world's own transaction/fence; it does not prove rejection. `apply` must compare the expected account, balance and version, and serialize all money/inventory/quest effects and older saves. It must durably preserve a fence until accounting acknowledgement. Identical operation retries must return the identical receipt. Concurrent callers must not cause a second effect.

The receipt fields are `phase,namespaceId,configHash,id,operationId,accountId,guid,kind,units,beforeUnits,afterUnits,beforeVersion,afterVersion,outcome,reason`. An applied receipt requires the exact computed result and version+1, with reason `applied`. Rejection requires unchanged money/version and a checked reason: `policy-rejection`, `stale-version`, `missing-character`, `owner-mismatch`, `overflow`, `insufficient-money`. Unknown/error/timeouts remain reserved. Receipt identity cannot be reused for another operation.

`ack({operation,receiptId,receiptHash,batchKey})` must durably/idempotently acknowledge the matching immutable receipt/accounting batch before releasing the world fence. It returns `{phase:'LIVE',namespaceId,configHash,operationId,receiptId,receiptHash,batchKey}`. A lost ack response is safe only if retry returns that same durable acknowledgement; the kernel's local lock remains until then. The world adapter must not be the current TEST bridge, whose fence lifetime is shorter.

All adapters run inside the trusted server boundary. No adapter accepts a browser-provided `verified` boolean or balance. Production proof providers require an independently operated/reviewed RPC trust policy; mocked RPC results are test evidence only.

## Remaining integration gates

This kernel does not connect stock `ModifyMoney`, quest/item/vendor/mail/AH/trade/start-money/GM/script paths, online/login/save fences, or a production worker. All positive game issuance must reserve a funded pool before the complete authoritative game event, and all transfers/escrows must conserve existing claims. The current stock world remains TEST and nonredeemable.

Withdrawals use this same conserved journal. Finalized treasury coverage includes every vault/world/pool/escrow/reservation claim and is checked before signing/submission, again after asynchronous work. Known deposit/withdrawal/reserve-proof slots form a durable observation floor: an earlier snapshot cannot authorize a later payment. If an outgoing chain debit is visible before local settlement, other signing conservatively freezes until reconciliation; no pending debit is subtracted speculatively and no shortfall releases funds. Importing the old prototype ledger would duplicate claims and is forbidden.

The withdrawal schema extension appends version 3 only after pre-extension operations and locks drain. Stop **all old worker/kernel processes before activation**, then use one reviewed version: rejection at database open cannot stop a connection already opened by old software. No upgrade clears a world/event/account lock or changes conversion. See [WITHDRAWALS.md](WITHDRAWALS.md) for the staged design, state contract and remaining signer/RPC trust gates.

Activation still requires actual world integration and queue/fault testing, final mint/conversion acceptance, funding/custody/fees, monitoring/reconciliation, access controls and launch review. A mint address alone cannot enable this system.

## Atomic multi-owner events (closed stage 2)

The facade additionally exposes `prepareEvent(quote)`, `advanceEvent(accountId,id)`, `event(accountId,id)` and `escrow(accountId,id)`. These methods share the same backing journal with deposits, vault grants and pool funding. Independent `prepareWorld` calls must never compose a trade, grouped reward, COD or auction outcome. Stage-2 account/resource locks also block the old one-character path. `advanceWorld` rejects batch IDs before contacting its adapter; `advanceEvent` likewise rejects single-character IDs.

An immutable, trusted server quote has exactly:

```text
{ id, accountId, eventId, family, planDigest,
  participants: [{accountId,guid,afterStateHash,action?:'keep'|'retire'}],
  escrows: [escrowAction],
  legs: [{id,from:owner,to:owner,units}] }
```

`planDigest` and per-character `afterStateHash` are lowercase SHA256 digests of the **complete quoted gameplay result**, including item/quest/trade/loot/AH state and callbacks; they are not browser assertions or just money hashes. `eventId` identifies one authoritative invocation and is globally unique across single and batch issuance. The coordinator `accountId` owns the operation lookup; it does not confer permission to invent other actors' consent. The private world quote must establish all eligibility and consent. Array bounds are 16 characters, 16 escrows and 32 individually identified legs. GUID/account membership is exact; unknown fields and duplicate actors/leg IDs are refused. Character and escrow units currently both use the conservative Classic cap.

Owner shapes are `{type:'character',accountId,guid}`, `{type:'escrow',id}` and `{type:'pool',id}`. Positive canonical game-unit strings convert through the immutable namespace factor; there is no floating point quote or rounding. All gross source outflows must already be available. Same-batch incoming claims cannot fund an outgoing leg, even when net balances would be nonnegative. All gross source holds and every account/character/escrow resource lock persist in one transaction. Recipients and fixed retained owners are fenced too. Pool holds come only from existing funded claims; transfer families cannot debit reward pools.

Families bound the allowed flows: `trade` between characters; `quest-reward` exact pool grants/requirements; `loot`, `vendor-sale`, `starting-money` funded issuance; `service` explicit sinks; `mail-send`, `mail-cod`, `mail-take`, `mail-return`, `mail-expire`; `auction-list`, `auction-bid`, `auction-settle`, `auction-cancel`; `escrow-recover`, `escrow-claim`, `escrow-delete`, `character-delete`. These describe private financial plans, **not implemented stock handlers**. For example a quest's XP conversion and reward amount are separate named legs; neither permits another callback to mutate money. AH settlement distributes existing bid/deposit claims and an explicit cut, with seller/refund beneficiaries checked. New bids needing a different funding owner require a distinct bid escrow and explicit old-bid refund.

Escrow creation is `{id,action:'create',kind:'mail'|'auction'|'trade'|'recovery',ownerAccountId,beneficiaryAccountId,retainedAccountId,expiresAt}`. The retained account must equal the original funding owner, and those identities/deadline are immutable. Existing actions are `{id,action:'keep'|'settle'|'return'|'expire'|'delete'}`. Return and authoritative deadline expiry keep all claims in the same escrow and switch its beneficiary to the retained owner. They are metadata-only conserved events, not timed refunds. No timer releases any pending financial hold. Returned/expired escrows cannot receive new claims. Mail checkout and auction checkout/refund must consume the complete source and persist `settled`. Deletion requires zero remaining claims after explicit relocation into the original owner's recovery escrow; terminal IDs cannot be reused. Character deletion similarly relocates every claim and permanently retires the GUID. Account deletion/reassignment still needs a reviewed durable financial-owner policy and actual core integration.

### Batch adapter and receipt

`authorizeEvent(normalizedQuote)` is a read-only trusted quote/snapshot adapter. It returns domain `{phase:'LIVE',namespaceId,configHash,requestHash}` where requestHash is SHA256 of the canonical normalized quote, plus complete `participants` and `escrows`. Participant snapshots have the single-character fields plus `gameplayStateHash`; versions and money must match existing allocation, with zero-only admission. Existing escrow snapshots have `id,kind,ownerAccountId,beneficiaryAccountId,retainedAccountId,expiresAt,state,moneyUnits,version`; a new escrow requires exactly `{id,absent:true}`. Quote failure must produce no gameplay effect. The kernel persists the normalized plan, expected/after snapshots, exact mutations, gross sources/targets and deterministic resource keys before any apply request.

`readEventReceipt(operation)`, `applyEvent(operation)` and `ackEvent({operation,receiptId,receiptHash,batchKey})` use the same durable private world-owner principles as single operations, extended to **all** participants, accounts, escrows and complete gameplay state. The actual core implementation must acquire persistent account/login/deletion and character/escrow/loot/AH/item/quest fences, CAS every expected version, queue after older saves, perform checked Begin/Execute/read-back/Commit on the same writer connection without reconnect, and publish memory/success only for the complete event. No later unversioned save may cross the fence. Unknown SQL outcomes must reconcile the entire bound receipt. Never synchronously wait on the world staging queue from a map worker whose completion the world is awaiting.

The complete receipt fields are `phase,namespaceId,configHash,id,operationId,accountId,eventId,requestHash,planDigest,outcome,reason,legs,participants,escrows,consumed`. `legs` must be the exact prepared array. Applied snapshots and version+1 must match the entire quoted result; rejected snapshots must exactly equal **all** before-states and consumed must be empty. Checked rejection reasons additionally include `missing-escrow` and `gameplay-conflict`. One omitted actor, wrong owner, extra nested reward, foreign/TEST domain or mismatched mutation denies the whole receipt, leaving every hold intact. Receipt identity is globally unique. One SQLite transaction moves the entire aggregate hold to all destinations (or restores all original sources), updates every tracked result, and records awaiting-ack. No actor settles independently.

Acknowledgement returns the same domain plus `operationId,receiptId,receiptHash,batchKey`; its durable identity must be recorded before the world releases **any** resource fence. Lost apply replies reconcile the complete receipt. Lost accounting-ack replies retry ack only; the local locks remain. Rejected or complete IDs stay durable and cannot be accepted again with another quote.

### Exact money authority and remaining gates

`applyPreparedLegs(operation, executor)` in `authority.mjs` is a synchronous, trusted-adapter primitive, exercised by the staged world fixture. It enumerates each character/escrow debit and credit separately, binding namespace/config/request/operation/event IDs, exact leg/side/owner, original version, and exact before/delta/after units. Each executor receives one one-use `ticket.apply(actualMutation, synchronousSink)`. It consumes that exact ticket before the sink invokes callbacks; mismatches, reuse, omission, Promises or reentry into **any** event poison the complete event even if an inner exception is caught. No next leg runs after poisoning. Retained tickets cannot be used later.

This helper neither authenticates an arbitrary caller's constructed operation nor undoes gameplay side effects: only the trusted persisted operation may reach it, and the adapter must roll back its entire staged transaction on error. A real C++ private sink capability and all raw field-writer guards, authoritative quoting, source audit/post-patch manifest, actual gameplay transactions and save/login/version fences are **still unimplemented**. A broad thread-local `moneyAllowed` flag is prohibited. Stage nested MoneyChanged→CompleteQuest→RewardQuest work in the original exact quote or a separate event after the current fence/ack; it must not inherit another leg's permission.

Schema 2 keeps configuration and all postings unchanged, adds escrow/retired state and multi-resource locks, and atomically upgrades a complete schema 1 only when every earlier operation is complete. Pending schema-1 journals fail closed and must be drained with their original reviewed adapter before upgrade. No TEST/prototype import or claim conversion occurs. Fresh independent review of this closed stage at `aba712b` found no remaining actionable findings; all 52 accounting tests and 9 TEST bridge tests passed under Node24. Production launch remains closed pending the full core/custody/funding/restore/monitoring gates above. See `ATOMIC-EVENTS.md` for the stage contract and verification plan.

Review hardening: a recovery escrow always has **owner = beneficiary = retained account = the predetermined recovery account**, on creation, reuse and every subsequent recovery/deletion hop. Existing recovery and returned/expired snapshots are checked against that invariant too; invalid historical fixture state is rejected, never repaired by moving claims. Automatically generated auction proceeds/refund mail likewise fixes all three identities to the predetermined seller/bidder, preventing a later return or expiry from redirecting it through an injected sender. Normal sender-authored mail retains its original funding owner as before. An invalid ticket from any earlier invocation poisons the **currently active** event as well as its original invocation; catching the error cannot authorize B or permit another B sink after poisoning.
