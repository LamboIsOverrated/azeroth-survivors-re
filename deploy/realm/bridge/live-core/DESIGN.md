# Funded C++ world adapter design

## Status and selected approach

Design only, 2026-10-28. No source patch or database operation is performed by this stage. The coordinator requested an actual source-backed plan and delegated implementation choices. The selected approach replaces each supported handler with checked preflight, detached gameplay staging, checked FIFO persistence and fenced publication. A late `ModifyMoney` hook cannot roll back previous item effects. A generic JavaScript simulation cannot establish core memory, SQL or callback behavior.

Use vendor sale as the first real handler slice, initially with an explicitly bounded item policy. A vault-to-character grant is smaller but does not prove an item transaction; full quest/trade/mail is larger and crosses extra persistence boundaries. Shared save/login/raw-field defenses are prerequisites, not later refinements.

The local read-only audit matched 2,208 covered files, all 226 review sites and 61 money API occurrences with no errors. ## Identity, protocol and limits

Journal `accountId` remains the web owner. C++ `WorldSession::GetAccountId()` and `characters.account` are realm account IDs. Persist a trusted immutable binding `(namespaceId, configHash, webAccountId, realmAccountId, guid, bindingVersion)`. Resolve it through server identity/account mapping, then compare session realm ID and locked SQL owner; never infer numeric equality or accept a browser-supplied mapping. Within a namespace each realm account and character has one journal owner; a conflicting mapping cannot create a second allocation for the same physical character. GUID/account reassignment requires a separate fenced migration, with pending events drained or explicitly recovered.

Retain the existing accounting [atomic event request/receipt](../accounting/ATOMIC-EVENTS.md), `event-plan.mjs`, `events.mjs` and `authority.mjs`. Canonical JSON sorts keys exactly as `amounts.mjs`; SHA256 hashes cover canonical bytes, not object memory layout. Account IDs are positive u32, GUIDs canonical u32 strings, game money `0..2147483646`, versions/atom arithmetic checked u64 strings, participants/escrows <=16 each, legs <=32. Enforce bounds before allocations and multiplication. Conversion comes only from immutable `atomsPerGameUnit`.

The private trusted coordinator serializes `authorizeEvent`, `readEventReceipt`, `applyEvent`, `ackEvent`. There is no public route or player-authored event plan. C++ independently checks family, plan bytes/digest, identities, expected versions, exact legs and after hashes; a caller cannot supply only a delta/hash and make it authority. Backend pool debit belongs to SQLite; the world receipt consumes the exact character mutations and proves the complete gameplay image.

Avoid recursive hashes: canonical gameplay-plan body contains before/after images, bindings, quote ID and source identity, but no requestHash or planDigest. Compute its planDigest, form the exact accounting request (including afterStateHash), then compute requestHash. Persist all three exact byte sequences and compare them on every hop. Cross-language golden fixtures must prove canonical bytes/hashes match.

An envelope carries explicit realm bindings alongside the unchanged journal-owner request. The gameplay plan binds those bindings and source pin. Receipt participant `accountId` still means journal owner; private envelope/session checks prove the realm owner. Namespace/config/operation/event/request hash cannot be rebound by transport retries.

## Required ownership and writer boundary

Introduce one process-wide coordinator consumed at the post-map barrier, plus per-resource leases spanning asynchronous stages. Memory actors are accessed only at that barrier or via an explicitly transferred owner thread. Leases are installed before releasing a quote and cover account, character, item, quest/buyback state and any future escrow/resource. Global ordering is lexical resource key order, matching sorted accounting resources; no network wait or map-worker join is held under a C++ mutex/SQL row lock. A failed later acquisition leaves no partial lease.

A lease fences *all* handlers/ticks/timers/scripts that could alter the actor's relevant inventory/quest/money image, saving, logout cleanup, map migration, account reassignment, deletion and login load/publish. Socket loss may detach the session but cannot run a stale logout save or drop the durable fence. Independent actors continue; never require the whole world empty. Mutation epochs are advanced by all permitted relevant nonfinancial changes; each deferred continuation checks actor/session generation, epoch and durable version before using pointers. Deferred work stores IDs/images, not Player/Item pointers.

Every character save/lifecycle writer must go through a versioned FIFO operation. A snapshot is captured once under the owner lease, carries binding/session generation and expected revision, and is checked on execution after all older queued writes. Queue position alone does not prevent a stale snapshot submitted later. Replace delete/reinsert and unconditional money writes for enrolled actors with checked updates; a stale save is rejected and the actor quarantined/reloaded, never silently retried with a newer version. Full-save helpers must expose immutable SQL/image builders and publish dirty-flag changes only on checked durable completion. No stock `_SaveInventory`, `_SaveQuestStatus` or `Item::SaveToDB` that mutates queues may run speculatively inside this protocol.

Keep financial `version` (the accounting participant version, incremented only by applied accounting events) separate from `gameplayEpoch/saveEpoch` (changed by ordinary relevant gameplay/save operations). Incrementing accounting version on an unrelated item save would make the kernel reject its own next snapshot. Ordinary saves preserve exact allocated money/financial version while CAS-checking their own epoch; event application checks both. Snapshot hashes include the relevant epoch/image so stale item saves cannot pass using only an unchanged money version.

Startup recovery acquires ownership before any normal login or cleanup; login checks both before scheduling the query holder and before consuming/publishing its results. SQL `online=0` is only data. Hydration must verify journal allocation, binding, version, money and complete image first; no clamping/unexplained stock balance adoption, no MoneyChanged issuance during load. Start with zero or a separately prefunded creation event. Pending fences survive restart and forbid deletion/import/restore/reassignment until reconciled.

## Durable state and transaction contract

Proposed CharacterDatabase additions, installed only in a disposable integration environment first:

- `realm_live_namespace`: exact source/protocol/config/schema identity; no TEST data migration.
- `realm_live_characters`: immutable binding, revision, gameplay hash, session generation, pending operation, lifecycle/retired state.
- `realm_live_events`: unique namespace/operation and event identity, full canonical request/plan bytes, before/after images and hashes, terminal receipt bytes, ack tuple and monotonic state. Operation/event tombstones never disappear.
- `realm_live_resources`: unique namespace/resource owner lease, operation binding; acquired all-or-none in sorted order.
- `realm_live_buyback`: complete sold/evicted item serialization, stable item GUID, owner, slot/cursor, price and absolute expiry. Hydrate/reconcile against inventory and items so no item has two locations. It does not hold currency; future buyback sinks use a separate funded event.

States: `quoted -> prepared -> applied|rejected -> acknowledged`; `quoted -> aborted` only with the explicit unreserved protocol below. Each transition is idempotent on identical bytes; conflict/unknown is never absence. Exact bytes and complete receipt remain immutable. Install the memory lease first, then persist the pre-event dirty snapshot, quote and resource leases in one checked FIFO transaction after older queued writes, checking the expected save epoch and financial revision. If baseline SQL fails, no authoritative quote is returned and the actor remains quarantined until checked recovery.

The existing JS accounting interface lacks two necessary capabilities: (1) a durable prepared-reservation attestation bound to `operationId/requestHash/planDigest`, consumed by C++ before apply; (2) a serialized `abortUnreservedQuote` that writes an accounting tombstone proving the operation has no reservation and can never be prepared later. Add these as private methods in a separately owned accounting change. Otherwise a failed pool reservation leaves the core lease safely held; a timeout, missing query row or timer must not unlock it. Before implementation, coordinator ownership must include these extensions. No unsigned player token can substitute for them.

Persistence runs as a single `SqlOperation` on the existing CharacterDatabase FIFO writer, with a pinned physical connection and checked session settings (autocommit, no automatic reconnect, storage engines, schema and namespace). Autocommitted durable lease precedes the effect transaction. Check Begin, every Execute, affected-row cardinality/readback, all version/ownership predicates and Commit. Row-lock durable resources/event before reading result, so recovery waits out a prior ambiguous commit. Missing-row proof uses a successful count/absence query; nullptr is an error. No replacement connection or statement retry mid-transaction. Any ambiguous begin/write/commit/rollback keeps the durable lease and quarantines the actor; recover only through locking receipt read on a healthy fenced writer.

The *same* SQL transaction writes all character money/version/image rows, all affected item/inventory/quest/buyback rows, evicted-item deletion, all future escrow/mail/AH effects, and one complete immutable applied receipt. A rejected receipt is durable only after proving expected gameplay unchanged and complete rollback/no apply; an execution failure is unknown, not policy rejection. It includes exactly the accounting expected state and consumed=[] for rejection. Do not call a stock helper that commits a nested mail or inventory transaction.

After successful commit, at the owner-thread barrier install the preallocated after image once and emit no external success yet. Publication must be allocation-free/no-callback; rebuild indexes and packet buffers during staging. Hold network output/update masks and any dependent callbacks behind the actor fence until durable accounting ack; generic world update flushing must obey that fence too. A publication fault quarantines actor/session, retains fences and reconstructs from the durable after image; it cannot turn applied into rejected or refund the pool. On crash before publication, login remains fenced while recovery loads that same image. No externally visible item/money update, successful opcode response or queued quest callback may precede complete durability. A dead socket drops packets, not state.

`readEventReceipt` returns exact complete durable bytes or checked absence while holding the operation fence. Accounting records receipt and settlement atomically, then sends the existing `receiptId/receiptHash/batchKey` acknowledgement. C++ verifies it against a private authenticated coordinator and exact receipt, persists ack first, and releases gameplay/resource fences only after publication/recovery is consistent. Replayed ack returns the same tuple after restart. Lost ack reply cannot unlock a second operation or duplicate gameplay; accounting subsequently marks complete and drops its own locks. No lease timeout refunds anything.

## Exact one-use money authority

Use a move-only `LegTicket` created only from the verified prepared plan. Bind namespace/config, request/operation/event, leg ID/side, journal and realm owner, GUID, owner version, exact signed delta and before/after units. Owner identity includes runtime actor/session generation. Consume before entering the staged money writer; the raw coinage store gets a separate one-use exact-range permit, closed before `MoneyChanged`. It cannot authorize another field, object, amount or callback. Two stock money sites in one quest are separate planned legs, never one ambient allow flag.

Stage context is poisoned by wrong/reused/expired/foreign tickets, omitted legs, nested/reentrant event creation, asynchronous continuation, or an unexpected raw-field attempt. Invalidate both the ticket's original context and the currently executing context, even when a callback catches an error. No further sink or commit can proceed after poison. Check complete consumption before constructing SQL/receipt.

Generic primitive coverage is byte-range overlap with PLAYER_FIELD_COINAGE, including a uint64 starting at COINAGE-1; byte/short/flags/float aliases and raw loads are covered before writes or update-bit publication. A private noncopyable hydration capability can install only the verified loaded exact value; zero creation has its own scope. Protected raw arrays require encapsulation or audited guarded stores for every direct writer, plus a reviewed post-patch coverage manifest. Merely wrapping SetUInt32Value is insufficient.

Failure must propagate as a checked result through the *replacement* handler/staging API. A defensive void setter cannot make arbitrary stock handler side effects transactional. Unsupported handler families are rejected at entry for enrolled actors; an unexpected out-of-stage bypass quarantines before persistence/publication and is a release blocker. Do not ship a partial guard that drops money but continues gameplay.

## Vendor-sale slice policy

First support full-stack sale (`count=0` resolves to actual count, or exact full count) of ordinary backpack items: no equipped item, container, duration/expiry/enchantment timers, negative-charge pricing, loot/trade/mail/AH ownership or script effect. Require no current cast to interrupt and no item-objective quest change or money-threshold completion/auto reward; conservatively reject such actors before any effect until the quest stage is implemented. These are explicit temporary slice restrictions, never silent partial success. Reject partial stacks before CloneItem/GUID allocation. Missing pool backing/overflow/cap returns an ordinary sale failure with the item and buyback unchanged.

Quote exact uint64 `SellPrice * count`, require positive result <= game cap and total before+price <= cap without clamping; do not use float pricing. Pin prototype/version/price, vendor identity/map/interaction validity, item GUID/entry/count/owner/location/full serialization, all buyback rows/cursor/victim, before money/version and relevant quest image. Revalidate vendor interaction on apply; stale interaction is a checked rejection. The one money leg is `pool:vendor-payouts -> character`, with game units converted once by accounting. Pool policy/funding is trusted configuration, never inferred from vendor stock or item value.

Build a detached immutable after image moving the original item into buyback and deleting exactly the selected evicted item, updating cursor/absolute expiry and money. Hash inventory, item bytes, buyback and quest state (including unchanged relevant quest status), plus binding/version. Stock helpers must be factored into pure choice/serialization routines or replaced; they must not run against live Player during staging. On success persistent item location, memory buyback fields and complete receipt agree after restart. Initially buyback purchase and every other financial family remain entry-rejected for enrolled test actors; TEST actors run the unchanged stock behavior. No LIVE flag is introduced by this design stage.

## Risks and acceptance boundary

Main engineering risk is complete writer/field/callback coverage, not transfer arithmetic. A first slice is incomplete until old saves, disconnect/login, buyback eviction/reload and actual MariaDB fault recovery pass through the new path. Freeze durations can be unbounded after uncertainty; show a pending state and provide deterministic recovery, never timeout release. Durable image/schema evolution must reject pending incompatible events and old worker processes must be stopped; open-time markers cannot revoke already-open code. External SQL/import/admin writers need separate operational fencing.

All unsupported quest/vendor/service/loot/trade/mail/AH/expiry/deletion routes require their own complete checked plans before a general funded realm can launch. C++ unit models alone, source audit alone or a successful source image build do not demonstrate this boundary. The current runtime stays TEST/nonredeemable throughout this work.
